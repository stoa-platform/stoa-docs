## Vue d'Ensemble

STOA Platform suit une architecture **cloud-native** déployée sur Kubernetes (ou Docker Compose pour l'évaluation locale) avec les principes suivants :

### Zones de Sécurité

| Zone | Niveau de Confiance | Composants |
|------|---------------------|------------|
| **Externe** | Non fiable | Clients API, Agents IA (Claude.ai, clients MCP), Interfaces Web |
| **DMZ** | Semi-fiable | Contrôleur Ingress, STOA Gateway (Rust), Envoy + STOA Link xDS ([ADR-073](/docs/architecture/adr/adr-073-adopt-envoy-data-plane)) |
| **Interne** | Fiable | API Control Plane, `stoa-operator`, Keycloak, Couche de Données |

### Composants Principaux

- **STOA Control Plane** — API de gestion Python/FastAPI, contrats UAC, catalogue et émission d'artefacts de politiques signés Ed25519
- **STOA Gateway (`stoa-gateway`)** — Runtime Rust/axum (Production / Maintenance selon [ADR-073](/docs/architecture/adr/adr-073-adopt-envoy-data-plane)) : MCP `2025-11-25`, routes de contrats REST, politiques tenant fail-closed et `ExtAuthzService` gRPC optionnel
- **Envoy upstream + STOA Link (`stoa-connect`)** — Plan de données L4/L7 cible via ADS mTLS loopback ([ADR-073](/docs/architecture/adr/adr-073-adopt-envoy-data-plane)), ainsi que les adaptateurs multi-passerelles (Kong, Gravitee, webMethods, Apigee, AWS, Azure)
- **Keycloak** — Realm unique `stoa`, groupes par tenant, OIDC/OAuth2 et claim JWT `tenant_id` vérifié ([ADR-074](/docs/architecture/adr/adr-074-tenant-model))

### Couche de Données

- **PostgreSQL** — Schéma partagé filtré par `tenant_id` (contrats, tenants, abonnements, audit)
- **OpenSearch** — Journaux API structurés, analytique et recherche d'audit
- **Redpanda (API Kafka)** — Événements asynchrones et métrologie (🔒 Interne Uniquement, [ADR-005](/docs/architecture/adr/adr-005-event-driven-kafka))
- **OpenBao (API Vault)** — Secrets et identifiants ([ADR-075](/docs/architecture/adr/adr-075-secrets-backend-openbao), déploiement partiel ; compatible HashiCorp Vault)

*(Note : STOA ne déploie pas Redis.)*

## Pipeline CI/CD

La chaîne de livraison suit une approche **GitOps** :

1. **Code** — Monorepo `stoa-platform/stoa` sur GitHub (incluant `charts/stoa-platform` et `charts/stoa-observability`)
2. **Build & Test** — GitHub Actions (lint, tests unitaires/intégration, scans sécurité, preuve réelle Envoy xDS)
3. **Package** — Images conteneurs signées et épinglées par digest sur GHCR (`ghcr.io/stoa-platform/*@sha256:...`)
4. **Deploy** — Synchronisation déclarative Argo CD ([ADR-007](/docs/architecture/adr/adr-007-gitops-argocd))

### Sécurité de la Chaîne d'Approvisionnement

- **SBOM** — Software Bill of Materials généré automatiquement en CI
- **Cosign** — Signature OIDC sans clé des images conteneurs
- **SLSA** — Attestations de provenance et déploiements Helm épinglés par digest

## MCP Gateway

La passerelle MCP permet l'intégration gouvernée avec les agents IA :

### Flux d'Exécution

1. L'agent IA envoie `POST /mcp` (`tools/call`) avec un JWT Bearer
2. STOA Gateway vérifie la signature JWKS RS256, `STOA_MCP_AUDIENCE` et le claim `tenant_id` ([ADR-074](/docs/architecture/adr/adr-074-tenant-model))
3. La passerelle évalue l'artefact de politique signé du tenant en mode fail-closed ([ADR-070](/docs/architecture/adr/adr-070-gateway-fail-closed-posture)) ainsi qu'OPA
4. La requête autorisée est transmise à l'API backend ou au serveur MCP cible
5. La réponse est retournée avec corrélation de trace et enregistrée dans les pipelines d'audit/métrologie

### Isolation Multi-Tenant

Chaque tenant ne voit que les outils rattachés à son `tenant_id` vérifié :

- **Parzival (`ioi`)** — `stoa_*`, `ioi:billing:*`, `ioi:inventory:*`
- **Sorrento (`gregarious`)** — `stoa_*`, `greg:oasis:*`, `greg:sixers:*`
- **Halliday (`cpi-admin`)** — Visibilité administrative inter-tenant
