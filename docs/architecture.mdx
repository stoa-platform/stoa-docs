## Overview

STOA Platform follows a **cloud-native** architecture deployed on Kubernetes (or Docker Compose for local evaluation) with the following principles:

### Security Zones

| Zone | Trust Level | Components |
|------|-------------|------------|
| **External** | Untrusted | API Clients, AI Agents (Claude.ai, MCP clients), Browser UIs |
| **DMZ** | Semi-trusted | Ingress Controller, STOA Gateway (Rust), Envoy + STOA Link xDS ([ADR-073](/docs/architecture/adr/adr-073-adopt-envoy-data-plane)) |
| **Internal** | Trusted | Control Plane API, `stoa-operator`, Keycloak, Data Layer |

### Main Components

- **STOA Control Plane** — Python 3.11 / FastAPI management API, UAC contracts, catalog, 6 gateway adapters (Kong, Gravitee, webMethods, Apigee, AWS API Gateway, Azure APIM — [ADR-035](/docs/architecture/adr/adr-035-gateway-adapter-pattern)), and signed Ed25519 policy bundle issuance
- **STOA Gateway (`stoa-gateway`)** — Rust/axum runtime (Production / Maintenance under [ADR-073](/docs/architecture/adr/adr-073-adopt-envoy-data-plane)): MCP `2025-11-25`, contract REST routes, fail-closed tenant policies, and optional gRPC `ExtAuthzService`
- **Upstream Envoy + STOA Link (`stoa-connect`)** — Target L4/L7 data plane via explicit opt-in loopback mTLS ADS ([ADR-073](/docs/architecture/adr/adr-073-adopt-envoy-data-plane)), alongside `stoa-connect` route adapters for Kong, Gravitee, and webMethods (Link policy sync is active for webMethods and Envoy ADS v1 filters, and rejected for Kong/Gravitee)
- **Keycloak** — Single `stoa` realm, top-level `/<tenant_id>` groups, OIDC/OAuth2, and verified `tenant_id` JWT claims ([ADR-074](/docs/architecture/adr/adr-074-tenant-model))

### Data Layer

- **PostgreSQL** — Shared schema scoped by `tenant_id` (PostgreSQL 15 in full Compose / production catalog, 16 in minimal R1 `quickstart/`)
- **OpenSearch** — Structured API logs, analytics, and audit search
- **Redpanda (Kafka API)** — Asynchronous events and metering (🔒 Internal Only, [ADR-005](/docs/architecture/adr/adr-005-event-driven-kafka))
- **OpenBao (Vault API)** — Secrets and credentials ([ADR-075](/docs/architecture/adr/adr-075-secrets-backend-openbao), MPL 2.0, partial rollout; compatible with HashiCorp Vault)

*(Note: STOA does not deploy Redis.)*

## CI/CD Pipeline

The delivery pipeline follows a **GitOps** approach:

1. **Source** — `stoa-platform/stoa` on GitHub (monorepo including `charts/stoa-platform` and `charts/stoa-observability`)
2. **Build & Test** — GitHub Actions (lint, unit/integration tests, security scans, plus a manual `workflow_dispatch` offline Envoy + Link xDS acceptance harness)
3. **Package** — Signed, digest-pinned container images on GHCR (`ghcr.io/stoa-platform/*@sha256:...`)
4. **Deploy** — Argo CD declarative sync ([ADR-007](/docs/architecture/adr/adr-007-gitops-argocd))

### Supply Chain Security

- **SBOM** — Software Bill of Materials generated in CI
- **Cosign** — Keyless OIDC container image signatures
- **SLSA** — Build provenance attestations and digest-pinned Helm deployments

## MCP Gateway

The MCP Gateway enables governed AI agent integration:

### Execution Flow

1. AI agent sends `POST /mcp` (`tools/call`) with a Bearer JWT
2. STOA Gateway verifies the RS256 JWKS signature, `STOA_MCP_AUDIENCE`, and `tenant_id` claim ([ADR-074](/docs/architecture/adr/adr-074-tenant-model))
3. Gateway evaluates the signed per-tenant policy bundle fail-closed ([ADR-070](/docs/architecture/adr/adr-070-gateway-fail-closed-posture)) and OPA policies
4. Authorized request is forwarded to the upstream API or MCP server
5. Response is returned with trace correlation and recorded in audit/metering pipelines

### Multi-Tenant Isolation

On `stoa-gateway`, MCP `tools/list` always filters tools by the caller's verified `tenant_id` claim (even when the caller holds `cpi-admin`; cross-tenant `cpi-admin` visibility applies only to Control Plane administrative APIs):

- **Parzival (`ioi`)** — `stoa_*`, `ioi:billing:*`, `ioi:inventory:*`
- **Sorrento (`gregarious`)** — `stoa_*`, `greg:oasis:*`, `greg:sixers:*`
